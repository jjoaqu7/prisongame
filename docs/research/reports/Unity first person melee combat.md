# Build the neighbor-cell fight rules-first

The research supports one consistent, **proposed** approach to real first-person melee for this game. The player gets four verbs: a quick attack, a hold-to-charge heavy attack, a block with a forgiving timed-block bonus, and a shove. The inmate telegraphs each attack with a long, obvious wind-up. Hits are found by script-driven swept physics queries during code-timed windows, not by trigger colliders on a swinging arm. Every combat rule is a plain C# class that receives the acting fighter explicitly and lives in its own assembly definition, so the compiler rejects rule code that reaches for input, the camera or the HUD. The first-person melee postmortems found, Arkane's Dark Messiah talk above all, name the failures this plan avoids: sluggish controls, unreadable enemy attacks, misjudged distance, and levels built before combat was settled. The open question with the largest effect on code is whether an armed player stops the inmate fighting back or only gains an advantage. Every reference found keeps armed fights two-sided, so this report proposes the advantage reading, and treating "the player is armed" as data the inmate reads makes either answer a tuning change rather than a rewrite. Co-op readiness costs little now: attack intents from a named fighter, time passed into rules, stable IDs, hit queries built from the attacker's own view, per-fighter hitstop instead of global time scaling, and no networking code. The same choices let edit-mode tests decide a fight in milliseconds. Thirteen decisions for the user are listed near the end, and ENCOUNTER-01 planning should follow them at **High** reasoning.

Labels follow the project rules. **Agreed** marks a user decision already recorded in [Gameplay](../../gameplay.md#neighboring-cell-inmate-encounter---agreed-purpose-and-real-combat-details-open) or the [development plan](../../development-plan.md#release-1-scope---agreed-september-25). Agreed so far: real combat; the player fist-fights the neighboring inmate, who fights back; nearby objects such as a book or rod work as weapons; the player kills him; and release 1 is single-player, with co-op planned for release 2. **Proposed** marks this report's recommendation, which is not a decision. **Open** marks a question only the user can settle. Sources marked "fan wiki" or "search excerpt" are lower confidence, and their mechanics numbers can depend on game patches. Facts about this project, such as file names and current behavior, come from reading its code on September 25, 2026.

## Four verbs and a long wind-up cover the first fight

The reference games converge on a small core. Condemned: Criminal Origins is the closest first-person match for improvised weapons. Players spend "a good 85% of the time swinging melee weapons," and "there is very little chance an enemy will miss... if they swing at you and you are standing still," so the skill it teaches is blocking and countering ([Game Developer](https://www.gamedeveloper.com/design/design-lesson-101---i-condemned-criminal-origins-i-)). Riddick: Escape from Butcher Bay is a first-person prison game with fist fighting. It rewards block timing on a sliding scale: an early or late block still reduces damage, and a perfectly timed one minimizes it ([Wikipedia](https://en.wikipedia.org/wiki/The_Chronicles_of_Riddick:_Escape_from_Butcher_Bay)). Zeno Clash's developers first built a lock-on so restrictive that players fought to the enemies' rhythm instead of their own. They moved away from it, admitting "we were convinced that we had to take control from the player" ([bit-tech](https://bit-tech.net/reviews/gaming/pc/zeno-clash-interview-into-the-unknown/3/)). Deep directional systems exist, including Kingdom Come's five attack zones and stamina-scaled blocking ([KCD wiki, fan](https://kingdomcomedeliverance.wiki.gg/wiki/Combat)) and Chivalry 2's direction-matched blocks, feints and ripostes ([Chivalry 2 wiki, fan](https://chivalry2.fandom.com/wiki/Combat)). Warhorse itself made parts of Kingdom Come 2 more accessible for players who found the first game too complex ([GOG](https://www.gog.com/en/news/read_our_exclusive_interview_with_warhorse_studios_about_kingdom_come_deliverance_ii)). Simpler sandbox games rely on hold-to-charge. The Escapists 2 attacks on click and charges extra damage on hold ([fan wiki](https://theescapists.fandom.com/wiki/Combat_System_%28The_Escapists_2%29)). Schedule I's punches are charged attacks in which holding raises "damage, impact force, stamina cost, and attack cooldown" ([fan wiki](https://schedule-1.fandom.com/wiki/Weapons)). Lethal Company's shovel winds up on hold and swings on release ([fan wiki](https://lethal-company.fandom.com/wiki/Shovel)).

**Proposed** verb set for the first fight: a **light attack** on a left-mouse tap; a **heavy attack** by holding and releasing (a separate heavy button is **Open**, and the input section explains what holding costs in latency); a **block** on the held right mouse button, where a timed block cuts damage to little or none and staggers the inmate while an untimed block reduces damage partly, as in Riddick; and a **shove** that pushes the inmate back to make space, following Dark Messiah's kick, which knocks enemies into hazards ([Wikipedia](https://en.wikipedia.org/wiki/Dark_Messiah_of_Might_and_Magic)). The first fight has no directional attacks, lock-on or combos. Whether stamina exists is **Open**. The references use stamina mainly to stop spamming, but in a one-on-one fight the recovery after each swing already does that job, so the proposal is to leave stamina out until playtests show spamming wins.

Every attack, the player's and the inmate's, has three phases. The **wind-up** is visible preparation and cannot hurt anyone. The **active window** is the only time the attack can hit. The **recovery** leaves the attacker open. GDKeys' combat-design guide sizes the wind-up as player reaction time (about 0.25 s), plus the time to perform the answer, plus a difficulty buffer: "typically 18+ frames at 30 fps", **about 0.6 s or more**. The same guide says input lag **under about 100 ms feels tight and above 160 ms feels sluggish** ([GDKeys](https://gdkeys.com/keys-to-combat-design-1-anatomy-of-an-attack/)). Arkane found the same thing from the player's side. Blind playtesters "hated the slow combat. First person calls for highly responsive controls," and anticipation animations were "a key element" that forced the team to redo work ([GDC 2007 talk text](https://archive.org/stream/GDC2007Colantonio/GDC2007-Colantonio_djvu.txt)). In first person, attacks at normal scale often play below the field of view. Arkane exaggerated them to stay centered on screen. Gauging distance was "never fully solved," so Arkane enlarged the player's hit zone to make near-misses count ([Game Developer](https://www.gamedeveloper.com/game-platforms/gdc-arkane-s-colantonio-takes-on-first-person-melee)). Mike Stout's rule, "if players don't understand the questions they are being asked, they actually can not play your game," argues for layering animation, sound and effects on every enemy wind-up ([Game Developer](https://www.gamedeveloper.com/design/enemy-attacks-and-telegraphing)). Tom Francis described Mirror's Edge's red-flash disarm as "a terrible challenge, relying either on using slow-mo so slow that the wait becomes boring, or learning the animations by rote." That is the case against frame-tight timing windows ([pentadact](https://www.pentadact.com/2009-01-25-the-combat-in-mirrors-edge-and-why-it-fucking-sucks/)). **Proposed:** the inmate uses high, wide swings that stay near screen center, with a grunt or whoosh just before each one, and the timed-block window is generous. Condemned's enemies feint to bait early blocks ([Wikipedia](https://en.wikipedia.org/wiki/Condemned:_Criminal_Origins)), but the first fight has no feints.

Impact comes from several small effects together. The best-studied is **hitstop**, a brief freeze of both fighters at the moment of contact. Sakurai freezes attacker and target, makes the freeze longer as damage rises, and caps it ([Source Gaming](https://sourcegaming.info/2015/11/11/thoughts-on-hitstop-sakurais-famitsu-column-vol-490-1/)). Vlambeer's list adds one- or two-frame pauses, a pixel or two of screen shake, and knockback on both sides ([Blue Tengu](https://www.bluetengu.com/2014/12/12/art-of-screenshake-experiments/)). Reactions must vary, and games fail in both directions. Tom Francis faulted Mirror's Edge because every attack produced the same stagger regardless of context ([pentadact](https://www.pentadact.com/2009-01-25-the-combat-in-mirrors-edge-and-why-it-fucking-sucks/)). Techland found in a combat update that "each attack felt excessively powerful" and rebalanced. That happened despite about 1,000 hit-reaction animations for one common enemy, combined from weapon, direction, body part and enemy state ([3DVF](https://3dvf.com/en/redaction/dying-light-2-stay-human-our-interview-with-techland-about-the-gut-feeling-update-focused-on-combat-animations-and-physics/)). A Game Rant opinion piece blames floaty first-person melee on swings "phasing right through an enemy." It credits Avowed's fix to "noticeable hitstop each time a weapon lands a blow" ([Game Rant](https://gamerant.com/avowed-melee-combat-first-person-rpg-weight-responsive-impact/)). Folmer Kelly warned that effects added without context fall flat ([Game Developer](https://www.gamedeveloper.com/design/video-indies-resist-the-urge-to-juice-it-or-lose-it-)), which argues for varying effects by hit type rather than turning them up. Accessibility guidelines ask for a way to disable camera motion the player did not cause, and for an adjustable field of view (FOV) ([Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/full-list/)), so screen shake must be optional. Arkane widened the FOV after combat worked and had to redo every character animation ([Game Developer](https://www.gamedeveloper.com/game-platforms/gdc-arkane-s-colantonio-takes-on-first-person-melee)). **Proposed:** fix the default FOV in the greybox stage, before any combat animation is authored.

## No reference lets a weapon end the opponent's fight-back

The user's wording was "if I am fist fighting then they would be able to fight back unless I pick up something like a weapon like a book or rod or something nearby." Gameplay records as **Open** whether an armed player stops the inmate fighting back or only gains a strong advantage. The references found keep armed fights two-sided in three ways. First, **enemies arm themselves**: unarmed Condemned enemies look around "frantically" for a weapon and rip pipes off walls ([Giant Bomb, search excerpt](https://giantbomb.com/wiki/Games/Condemned_Criminal_Origins)). Second, **either side can disarm**: Riddick grabs an armed enemy's weapon with a timed press and turns it on him ([Wikipedia](https://en.wikipedia.org/wiki/The_Chronicles_of_Riddick:_Escape_from_Butcher_Bay)), and Zeno Clash lets players disarm enemies and throw stunned ones ([GameFAQs, fan guide](https://gamefaqs.gamespot.com/xbox360/975437-zeno-clash-ultimate-edition/faqs/59819)). Third, **weapons trade off**: every Condemned weapon trades damage, speed, block and reach ([GameFAQs, fan guide](https://gamefaqs.gamespot.com/pc/926310-condemned-criminal-origins/faqs/49952)); Condemned 2's fists are weaker and shorter than weapons but faster and able to chain ([Wikipedia](https://en.wikipedia.org/wiki/Condemned_2:_Bloodshot)); and Dying Light's weapons degrade with each hit ([fan wiki](https://dyinglight.fandom.com/wiki/Weapons_%28Dying_Light%29)). No source found has a weapon that stops an opponent from fighting back.

The project rules ask for an honest assessment when an idea looks weak, and the "stops fighting back" reading has a real design problem. The book and rod are nearby on purpose, so the fight would end the moment the player picks one up. The agreed "real combat" would then reduce to a pickup check followed by free hits. A book ending a grown inmate's ability to fight also reads oddly. **Proposed:** the advantage reading. The armed player hits harder, reaches further, and staggers the inmate more reliably, which interrupts his wind-ups. The inmate still attacks, but keeps more distance and becomes more likely to flee or yield as his health drops. A later addition could let him grab the other object or try to disarm the player, as Condemned and Riddick do. Whichever reading the user picks, the inmate's decisions should read the player's weapon as data: preferred spacing, flee threshold, and how easily he is staggered. It should not add separate states. Switching readings later then means changing numbers in an asset.

**Proposed** weapon profiles follow Condemned's stat trade-off. The book is fast and low-damage, breaks after a few hits, and could block slightly better. The rod is slower, hits harder, reaches further and lasts. Tracking durability as a small hit count avoids a repair economy in release 1. Throwing the book as a one-time stun is cheap to build, but it is **Open**, because the references support throwing people (Zeno Clash) and discarding weapons more than a thrown-object combat system. Later, Schedule I's pattern that melee draws less police attention than guns ([TheGamer](https://www.thegamer.com/schedule-1-all-weapons-baseball-bat-revolver-fight-npcs-how-to-guide/)) maps onto guard-response tiers: fists, then an improvised weapon, then a shiv.

The kill is **Agreed**; how it happens is **Open**. Prison and sandbox games default to knockouts. The Escapists 2 sends a knocked-out player to the infirmary and takes their contraband ([fan wiki](https://theescapists.fandom.com/wiki/Combat_System_%28The_Escapists_2%29)), Bully fights end in a knockout or someone running away ([fan wiki](https://bully.fandom.com/wiki/Fighting)), and Party Animals characters wake up again ([TheGamer](https://www.thegamer.com/party-animals-how-to-play-guide/)). Games that allow killing make it a distinct act. Condemned 2's environmental finishers always kill ([Wikipedia](https://en.wikipedia.org/wiki/Condemned_2:_Bloodshot)). Sleeping Dogs' environmental kills work regardless of health ([beforeiplay, fan](https://beforeiplay.com/wiki/Sleeping_Dogs)). Kingdom Come lets the player accept or refuse an opponent's surrender ([KCD wiki, fan](https://kingdomcomedeliverance.wiki.gg/wiki/Combat)). Dishonored tracks killing in world state and darkens the world in response ([Wikipedia](https://en.wikipedia.org/wiki/Dishonored)).

**Proposed:** a two-stage outcome. Zero health leaves the inmate downed, and killing him is a separate, deliberate action. This makes the kill a readable choice and gives the fight a clear end state. It also lets later gang fights and guard takedowns end non-lethally without redesign. The simpler alternative, where zero health means dead, removes one state and one input. What happens when the player loses is also **Open**. It needs an answer before ENCOUNTER-01 because the inmate fights back. Options include an Escapists-style knockout with a penalty or a reload of the last manual save.

No reference found combines cute characters with deliberately killing a named person, so the tone of this kill has no close precedent. Manveer Heir's analysis of Condemned says combat "should complement the atmosphere and feel of the game being created" ([Game Developer](https://www.gamedeveloper.com/design/design-lesson-101---i-condemned-criminal-origins-i-)). For the agreed eerie-cozy [art direction](../../art-and-tone.md), that points to eeriness through restraint rather than gore: sound dropping out, and the body staying in the cell. This is **Proposed**; the choice is **Open**. How much blood appears also has a practical cost. ESRB separates "Fantasy Violence," which is "easily distinguishable from real life," from "Intense Violence," which "may involve extreme and/or realistic blood, gore" ([ESRB](https://www.esrb.org/ratings-guide/)). Schedule I's Steam page discloses "non-realistic violence" ([Steam](https://store.steampowered.com/app/3164500/Schedule_I/)). These definitions show where bloodless, stylized fighting lands; they do not predict a rating.

## Swept queries, ragdoll hurtboxes and one camera carry the Unity side

### Find hits with timed sweeps, not trigger colliders

Unity publishes no recommended melee hit-detection method, but its documentation rules out the obvious one. Sweep-based continuous collision detection "cannot predict collisions that might happen if the physics body rotates" ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/sweep-based-ccd.html)). A swung rod or fist moves in an arc, so a trigger collider on the weapon can pass through a target between physics steps.

The garbage-free query functions are current in 6.3. They include `OverlapCapsuleNonAlloc`, `CapsuleCastNonAlloc` and `SphereCastNonAlloc`. Each one writes into a buffer you reuse and never grows it. When the buffer is full, the call returns the buffer length. The order of results is not documented ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.OverlapSphereNonAlloc.html); [Physics class](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.html)).

A Unity forum thread reaches the same place. Raycasts are precise but "clunky," `OverlapCapsule` works better than a sphere at close range, and each attack needs a list of targets already hit ([Unity Discussions](https://discussions.unity.com/t/raycast-or-overlapsphere-for-melee-weapons/927490)). Arkane's 2007 fix was to "apply multiple hit zones that follow the sword animation, and apply the first damage only" ([GDC 2007 talk text](https://archive.org/stream/GDC2007Colantonio/GDC2007-Colantonio_djvu.txt)).

A **hurtbox** is a collider on a fighter's body that attack queries look for. **Proposed** procedure: when a swing's active window opens (its timing comes from weapon data), the combat code clears a per-swing `HashSet` of fighters already hit. On each combat tick inside the window, it takes two or three points along the striking part (the fist, or the rod from grip to tip) and casts a capsule or sphere from each point's previous position to its current one, with a layer mask containing only the `Hurtbox` layer and an explicit `QueryTriggerInteraction`. It then maps each collider to its owning fighter, skips fighters already in the set, and passes each new hit to the rules. For the player, build the points from the gameplay camera's position and forward direction plus the weapon's reach and radius, swept across the swing arc. Never build them from the first-person arm model. That model is drawn with a different FOV and offset (next subsection), so it is not where it appears on screen. Make the radius generous, as Arkane did. `Physics.ClosestPoint` gives a contact point for effects and knockback direction.

NPC hurtboxes ride animated bones, so call `Physics.SyncTransforms()` once before each batch of queries. Unity syncs automatically only before a physics step, and it calls the explicit sync "expensive if called every frame unnecessarily" ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.SyncTransforms.html)). The older `Physics.autoSyncTransforms` switch is documented in 6.0 ([Unity](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Physics-autoSyncTransforms.html)) but missing from the 6.3 scripting reference. Check its behavior in the Editor before relying on it.

### Reuse the ragdoll colliders as hurtboxes, and push with CharacterController.Move

The Ragdoll Wizard (GameObject > 3D Object > Ragdoll…) still generates per-bone Rigidbodies, colliders and joints from a skinned character in 6.3 ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/wizard-RagdollWizard.html)). **Proposed:** run the wizard once on the shared inmate rig. While the inmate lives, keep those Rigidbodies **kinematic** (animation moves them; physics forces do not), put their colliders on a `Hurtbox` layer, and give each collider a small `HurtboxPart` component that holds the body part, a damage multiplier and the owning fighter. The same colliders then become the death ragdoll, so there is one collider set to maintain.

The Layer Collision Matrix controls physical contacts ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/LayerBasedCollision.html)). Its page does not say whether it also filters queries, so every query passes an explicit layer mask. Suggested layers are `Player`, `NPCBody`, `Hurtbox`, `HeldItem`, a render-only `Viewmodel`, and `Ragdoll`. Set `Hurtbox` not to collide with `Player`, `NPCBody` or itself, so bone colliders never shove the movement capsules.

Unity's performance advice is to set Animator culling to Cull Completely ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/MecanimPeformanceandOptimization.html)), which stops animating characters that are off-screen. That conflicts with melee: an inmate attacking from outside the view would freeze its hurtboxes and its timing. **Proposed:** fighters in combat use Always Animate.

`CharacterController` "is not affected by forces and will only move when you call the Move function" ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/CharacterController.html)). **Proposed** knockback: each fighter's mover keeps an external velocity. A hit adds to it, and it decays every frame. It is added to the player's `Move` delta, and to the scripted displacement in `InmateMotion`. `InmateMotion` currently moves the inmate by setting `transform.position` after ground checks, not through a `NavMeshAgent`.

### Draw the first-person arms with a Render Objects feature

The **viewmodel** is the first-person arms and held item, drawn only for the local player. No arms exist yet.

Unity's URP FPS Demo puts first-person objects on a layer removed from the renderer's normal layer masks. It draws them with Render Objects renderer features at a 40° FOV override, with stencil settings to handle transparent parts ([Unity GitHub wiki](https://github.com/Unity-Technologies/UniversalRenderingExamples/wiki/FPS-Demo)). The 6.3 Render Objects feature exposes the needed camera overrides: Field of View, Position Offset and Restore ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/renderer-features/renderer-feature-render-objects.html)). Camera stacking with a second overlay camera also works. Unity's only performance note on stacking is to trim each camera's culling mask ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/camera-stacking.html)).

URP Compatibility Mode is removed in 6.3 ([Unity upgrade guide](https://docs.unity3d.com/6000.3/Documentation/Manual/UpgradeGuideUnity63.html)), so custom render passes from older tutorials will not work. The built-in feature needs no render-pass code. Forum users report the environment drawing over the weapon with the official setup. They fixed it by drawing the weapon with depth testing off, or by using an overlay camera ([Unity Discussions](https://discussions.unity.com/t/urp-fps-object-camera-clipping-into-walls-official-srp-tutorial/835118)).

**Proposed:** follow the FPS Demo with a `Viewmodel` layer and one opaque Render Objects pass. Add transparent passes only if needed. No source covered screen-space ambient occlusion or other depth-reading effects near the arms, so verify those in the Editor. When the player holds the book or rod, move its renderer to the `Viewmodel` layer under a hand socket, or spawn a separate viewmodel prefab. Disable its world colliders while held, and restore both on drop. The held item already lives on `PlayerInteraction.HeldItem`.

### Keep attack timing in data and let animation follow

Store wind-up, active and recovery durations in the weapon definition, so the rules run the same timeline with or without an Animator. That matters for tests and for a later co-op host. Community documentation for Chivalry 2 shows the cost of the alternative. Its melee netcode is "very sensitive to host and client FPS," producing "delayed hits, swing-throughs" at low frame rates ([Chiv2-Community GitHub](https://github.com/Chiv2-Community/C2ServerAPI)). Animation events can still mark moments with an int attack ID ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/script-AnimationWindowEvent.html)), but they only notify the rules and never apply damage.

**Proposed:** one base upper-body controller, plus an Animator Override Controller for each weapon class (fists, short blunt such as the book, long blunt such as the rod). Each override swaps clips but keeps one state machine. Unity warns to use normalized exit times, because a shorter override clip can skip an exit time given in seconds ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/AnimatorOverrideController.html)). Flinches go on an additive layer with an upper-body Avatar Mask, and full-body staggers and knockdowns go on an override state; a layer at zero weight is skipped and costs nothing ([Unity layers](https://docs.unity3d.com/6000.3/Documentation/Manual/AnimationLayers.html); [Mecanim performance](https://docs.unity3d.com/6000.3/Documentation/Manual/MecanimPeformanceandOptimization.html)). Player attacks move the body through scripts, not root motion, so clip motion never drives the camera. Clips transfer between different rigs "only... for humanoid models with a configured Avatar" ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/Retargeting.html)), so the separate first-person arms rig can stay Generic.

### Switch to ragdoll in a fixed order at death

**Proposed** order when the rules mark the inmate dead: disable the Animator, set every ragdoll Rigidbody non-kinematic, move the bone colliders from `Hurtbox` to `Ragdoll`, disable the inmate's movement collider, and only then apply `AddForceAtPosition` with `ForceMode.Impulse` at the struck bone. Order matters because setting the velocity of a kinematic body "will have no effect" ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Rigidbody-linearVelocity.html)). Unity 6 also changed how `AddForceAtPosition` computes torque in the `VelocityChange` and `Acceleration` modes ([Unity 6 upgrade guide](https://docs.unity3d.com/6000.3/Documentation/Manual/UpgradeGuideUnity6.html)).

Apply Unity's ragdoll stability rules at setup ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/RagdollStability.html)): angular limits of at least 5 to 15° or zero, joint projection on, mass ratios under 10×, and Transform scale of 1. Also lower `maxDepenetrationVelocity`, because bodies will spawn close to cell walls and bunks.

The alternative is a death animation, which is cheaper and plays the same way every time. Arkane dropped physics-driven "ragdoll hits" as a performance cost and "made tons of animations" instead ([GDC 2007 talk text](https://archive.org/stream/GDC2007Colantonio/GDC2007-Colantonio_djvu.txt)). Which to use is **Open**. Automated checks assert on the rules state and component flags, never on the final ragdoll pose.

### Read input in one local adapter and pass intents

An **intent** is a small record of what a fighter wants to do: light attack, heavy start, heavy release, block start or block end. It carries a time and the fighter's ID. Today `PlayerInteraction` polls E, R and Q through `Keyboard.current`. `FirstPersonController` builds its own move and look actions. No mouse button is bound. Both mouse buttons are therefore free, and attacking stays separate from E. That answers the concern recorded in Gameplay that a fight should not start from an accidental talk or door press.

Input System interactions support tap-versus-hold on one button, checked "in the order they are present on the Binding" ([Input System docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/Interactions.html)). But a `tap,hold` binding cannot fire a light attack until the button is released or the tap time runs out. That delay works against the 100 ms target, and a separate heavy button avoids it (**Open**).

Input buffering is not an engine feature, and designers disagree on it. God of War has "GENEROUS input buffering," while Sekiro has "ZERO input buffering on normal attacks" ([Jason de Heras](https://www.jasondeheras.com/gamedesign/2021/2/11/meleecombatdesign)). **Proposed:** a local `PlayerCombatInput` adapter turns actions into intents and keeps one buffered intent. The buffered intent expires after about 150 ms, a forum-level starting value. The fighter consumes it when its state allows. Only this adapter touches `InputSystem`.

### Store weapons as ScriptableObjects and keep changing values elsewhere

A **ScriptableObject** is a Unity data asset edited in the Inspector and shared by everything that references it. Unity describes it as a shared data container. A built game can only read it, but changes made in the Editor during Play mode persist into the asset ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/class-ScriptableObject.html)). That is a common source of "numbers changed after testing" bugs.

**Proposed:** a `MeleeWeaponDefinition` asset holds an id and display name, base damage and knockback impulse, reach, hit radius and sweep points, per-attack wind-up, active and recovery times, heavy charge time, block reduction, optional durability, the arms and NPC override controllers, the viewmodel prefab, and hit sounds and effects. Fists are a default definition used when nothing is held. `PrototypePickup` gains an optional reference to a definition. The book and rod are then two assets, and one item identity serves pickup, inventory and combat. Values that change during play live in plain C# objects per fighter or per item instance: current durability, cooldowns, and the per-swing hit set. Naughty Dog's structure for The Last of Us Part II has the same shape. Attack data carries timeline events for hit frames and invulnerability, separate from NPC behavior data ([Game Developer](https://www.gamedeveloper.com/design/how-naughty-dog-defined-melee-attacks-and-behaviors-in-i-the-last-of-us-part-ii-i-)).

### Apply hitstop per fighter, never through Time.timeScale

Setting `Time.timeScale` to zero is the common shortcut, and it fails here for two reasons. Unity documents that `FixedUpdate` and `WaitForSeconds` coroutines stop at zero, and that changes apply only on the next frame ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Time-timeScale.html)). Sakurai notes that a shared freeze hands a third player a free hit ([Source Gaming](https://sourcegaming.info/2015/11/11/thoughts-on-hitstop-sakurais-famitsu-column-vol-490-1/)), which rules it out for co-op.

**Proposed:** hitstop freezes only the attacker's and victim's Animators (`speed = 0`) and pauses those two fighters' combat timelines, restoring both after the duration measured in unscaled time. Camera kick is a decaying offset on a child pivot of the camera, and it never moves the transform the rules read for aim. Cinemachine is not installed; its Impulse Listener is the packaged alternative ([Unity](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/CinemachineImpulse.html)). Hit flashes use a cached per-renderer material instance with a flash property. Objects using `MaterialPropertyBlock` lose SRP Batcher compatibility ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/SRPBatcher-Materials.html)), while separate materials sharing a shader variant still batch ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/SRPBatcher.html)).

Coding agents often write pre-Unity-6 names, so the implementation brief should list the current forms:

| Older code an agent may write | Unity 6.3 form | Source |
|---|---|---|
| `rb.velocity`, `rb.drag`, `PhysicMaterial` | `linearVelocity`, `linearDamping` / `angularDamping`, `PhysicsMaterial` | [Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Rigidbody-linearVelocity.html); full rename list from secondary sources |
| Custom `ScriptableRenderPass.Execute` passes | Render Graph `RecordRenderGraph`, or the built-in Render Objects feature | [Unity 6.3 upgrade](https://docs.unity3d.com/6000.3/Documentation/Manual/UpgradeGuideUnity63.html); [Render Graph](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/render-graph-write-render-pass.html) |
| `AddForceAtPosition` with `VelocityChange` or `Acceleration` | Torque computed differently; multiply by mass and use `Impulse` or `Force` for the old result | [Unity 6 upgrade](https://docs.unity3d.com/6000.3/Documentation/Manual/UpgradeGuideUnity6.html) |
| Relying on `Physics.autoSyncTransforms` | Absent from the 6.3 reference; call `Physics.SyncTransforms()` explicitly | [Unity 6.0 page](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Physics-autoSyncTransforms.html) |

## A code-first state machine runs the inmate, with an attack budget ready for gangs

A **finite state machine (FSM)** keeps a fighter in exactly one named state, such as Approach, WindUp or Recover, with coded rules for moving between states. A hierarchical FSM nests state machines inside states. Game AI Pro calls FSMs "the most common behavioral modeling algorithm used in game AI programming today." It warns that once an FSM has "10, 20, or 30 existing states," adding one "can be extremely difficult and error-prone." A hierarchical FSM with a "history state" returns an interrupted fighter to where it was without duplicating states ([Game AI Pro ch. 4](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter04_Behavior_Selection_Algorithms.pdf)). The same chapter weighs the alternatives. Behavior trees keep behaviors unaware of each other at a higher running cost, utility systems are "often somewhat unpredictable" and hard to tune, and goal-oriented planners remove "a lot of the authorial and directorial control," so characters "can become loose cannons." Doom (2016) shipped its combat AI on hierarchical FSMs, not behavior trees ([Game Developer](https://www.gamedeveloper.com/design/cyber-demons-the-ai-of-doom-2016-)).

Unity's own option carries risk. The Behavior package is released, at version 1.0.16 from May 2026, as "a graph-based tool to create and run behavior trees" ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/com.unity.behavior.html); [changelog](https://docs.unity3d.com/Packages/com.unity.behavior@1.0/changelog/CHANGELOG.html)). Its team was hit by layoffs in February 2025 ([Unity Discussions](https://discussions.unity.com/t/an-update-on-behavior/1598451)). On May 1, 2026, Unity said its approach "will shift toward maintenance and stability rather than new feature development" ([Unity Discussions](https://discussions.unity.com/t/update-on-behavior-package-support-and-team-presence/1718517)). Graph assets are also harder for coding agents to write and review than C#. **Proposed:** do not adopt the package now. Revisit it only if a hierarchical FSM hits transition overload, and compare it then against a small C# behavior tree.

**Proposed:** the inmate brain is a plain C# FSM with about eleven states: Idle, Approach, Circle, WindUp, Attack, Recover, Block, Stagger, Flee/Yield, Downed and Dead. That sits below the chapter's pain threshold, and Stagger and Yield become interrupt super-states once the hierarchy is added. The brain is a class with `Tick(dt, perception)` that returns intents (move to, face, start attack X, block), and a separate MonoBehaviour executes them through `InmateMotion` and the Animator. Each brain gets its own seeded `System.Random`, because Unity's `UnityEngine.Random` is "a static class, and so its state is globally shared" and Unity points to `System.Random` instances for independent streams ([Unity](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Random.html)); otherwise sounds and effects that call the shared generator would change fight outcomes. Every transition, attack grant and stimulus is logged as a structured record (time, fighter ID, from-state, to-state, reason), so tests can assert on the sequence and a debug overlay can draw it. Moving, facing, attacking and blocking are self-contained classes that can later become behavior-tree leaves or utility options unchanged.

The inmate's attacks use the same data as the player's: wind-up, active window, recovery, reach, damage, stagger power, attack weight and cooldown. Shipped melee games signal attacks with a preparation pose, a weapon glint and a sound (DmC). They space one enemy's attacks two to three seconds apart, and avoid attacking a player still staggered from a previous hit ([Game Developer, Vossen](https://www.gamedeveloper.com/design/enemy-design-and-enemy-ai-for-melee-combat-systems)). Doom grades pain reactions from "mild twitching" to "falters and push back," and only the heavier grades interrupt behavior ([Game Developer](https://www.gamedeveloper.com/design/cyber-demons-the-ai-of-doom-2016-)). Sifu fills a "structure" gauge from blocked attacks until the guard breaks ([SVG, search excerpt](https://www.svg.com/760718/how-sifus-structure-system-actually-works/)). **Proposed:** a stagger meter filled by hits, scaled by weapon, with graded reactions. Low health triggers flee or yield with **hysteresis**: separate enter and exit thresholds, so the inmate does not flip between fleeing and fighting. Later, an inmate that has been blocked several times can start to feint, as Condemned's enemies do.

One inmate needs no coordination, but gangs will, and the references show three ways to limit simultaneous attackers. Kingdoms of Amalur gave each target a capacity and each creature and attack a weight. With capacity 12, a soldier (weight 4) and a troll (weight 8) fill it, and a second soldier "must wait outside the grid area." A central stage manager assigns positions, attackers give up their slot "immediately after launching an attack," and difficulty changes a few capacity numbers ([Game AI Pro ch. 28](http://www.gameaipro.com/GameAIPro/GameAIPro_Chapter28_Beyond_the_Kung-Fu_Circle_A_Flexible_System_for_Managing_NPC_Attacks.pdf)). Doom used per-attack-type tokens that demons request, release and steal ([Game Developer](https://www.gamedeveloper.com/design/cyber-demons-the-ai-of-doom-2016-)). Dark Messiah allowed "no more than 2 enemies in contact within the same Squad" ([GDC 2007 talk text](https://archive.org/stream/GDC2007Colantonio/GDC2007-Colantonio_djvu.txt)). God of War 3's designers also avoided off-screen attacks as "really hard to read" ([Vossen](https://www.gamedeveloper.com/design/enemy-design-and-enemy-ai-for-melee-combat-systems)). **Proposed:** the inmate asks "may I attack?" from day one. A per-target coordinator answers, and in the first fight it always says yes. Because the budget belongs to the target, the same code later serves inmate brawls and two co-op players. The off-screen check uses the target player's facing from game state, not a render camera.

At melee range, movement needs care. Unity's NavMesh documentation describes two valid couplings: animation follows the agent, or the agent follows animation. Mixing them creates "race conditions" ([Unity](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/MixingComponents.html)). An agent and an obstacle on the same object leave "the agent trying to avoid itself" (same page). Built-in avoidance "only considers the next immediate collisions" ([Unity](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavInnerWorkings.html)).

**Proposed:** keep the current scripted movement for the cell fight. Inside attack range, stop path-following and rotate to face the target manually. Use separate enter and leave distances. Move to slot positions around the target rather than to the target itself. If wider prison areas later adopt `NavMeshAgent`, have the animation follow the agent with in-place clips, and switch downed or dead bodies to a carving obstacle. Cells are choke points. Splinter Cell: Blacklist tagged each area with "the number of NPCs that should enter that area for search or combat" ([Game AI Pro 2 ch. 28](http://www.gameaipro.com/GameAIPro2/GameAIPro2_Chapter28_Modeling_Perception_and_Awareness_in_Tom_Clancy%27s_Splinter_Cell_Blacklist.pdf)), which fits capping the number of fighters inside a cell.

Fights will need to reach guards and gangs. In Splinter Cell: Blacklist's perception model, every sound event has "a radius and priority." Distance is measured along room-to-room paths, because straight lines meant "the player would be heard through walls." For fairness, off-screen NPCs hear certain events at half range, and the first NPC to witness an event claims it ([Game AI Pro 2 ch. 28](http://www.gameaipro.com/GameAIPro2/GameAIPro2_Chapter28_Modeling_Perception_and_Awareness_in_Tom_Clancy%27s_Splinter_Cell_Blacklist.pdf)). Bethesda's Creation Kit uses a four-value faction relation (Enemy, Neutral, Friend, Ally) plus a per-NPC setting for helping friends and allies ([Fallout Wiki, search excerpt](https://fallout.wiki/wiki/Resource:Creation_Kit/Faction)). **Proposed:** hits, shouts and falls post stimulus events carrying a type, position, radius, priority and instigator ID. A hearing check measured along cell, corridor and wing connections adds to the existing per-player suspicion, which already advances through an explicit `GuardSuspicion.Step(seconds)`. One guard claims each fight. How guards respond to the neighbor-cell kill is **Open**.

## Assembly definitions turn the rules-input split into a compile error

An **assembly definition** (an `.asmdef` file) compiles the scripts in its folder into a separate library with declared dependencies. Unity says assemblies help you "think clearly about the architecture of your code" and "reduce unnecessary recompilation time" ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/assembly-definition-files.html)). Four reference rules matter here. Unity's default script assembly, `Assembly-CSharp`, references every custom assembly; a custom assembly may not reference `Assembly-CSharp`; two assemblies may not reference each other; and with Auto Referenced turned off, the default assemblies no longer recompile when the custom one changes ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/assembly-definitions-referencing.html)). Edit-mode and play-mode tests live in different assemblies ([Unity](https://docs.unity3d.com/6000.4/Documentation/Manual/test-framework/edit-mode-vs-play-mode-tests.html)). Unity's organization guide says "there is no single way to organize a Unity project." It advises against spaces in names and recommends a separate folder for experiments, plus namespaces for modules ([Unity](https://unity.com/how-to/organizing-your-project)). Today, all 41 scripts sit in `Assets/Prototype/Scripts` under the namespace `PrisonGame.Prototype`, with no assembly definitions.

The reference rule does the enforcement the project wants. New combat code in a `PrisonGame.Combat` assembly cannot see `PlayerInteraction`, the HUD or any prototype camera script, so a rule that reads input or the camera fails to compile. The glue between the prototype and combat code lives on the prototype side, which may reference the new assembly. That glue covers the input adapter, the pickup's weapon reference, HUD listeners and save hooks. Moving existing code then runs bottom-up: data types and plain rule classes first, then each MonoBehaviour once everything it touches has moved. **Proposed** layout:

```
PrisonGame/Assets/
  PrisonGame/                                  production content (new)
    Scripts/
      Core/Runtime/          PrisonGame.Core.asmdef        EntityId, shared event types
      Combat/Runtime/        PrisonGame.Combat.asmdef      rules, fighters, hit queries, weapon data
      Combat/Tests/EditMode/ PrisonGame.Combat.Tests.EditMode.asmdef   (Editor-only test assembly)
      AI/Runtime/            PrisonGame.AI.asmdef          inmate brain, attack coordinator (references Combat)
    Tests/PlayMode/          PrisonGame.Tests.PlayMode.asmdef
    Data/Weapons/            Fists.asset, Book.asset, Rod.asset
  Prototype/                                   existing sandbox, stays in Assembly-CSharp
    Scripts/                 + PlayerCombatInput.cs and glue to HUD, save and pickups
```

A small `Core` assembly holds IDs and shared event types. Combat, AI and later Save depend on it instead of on each other, which avoids forbidden cycles. Namespaces mirror assemblies, for example `PrisonGame.Combat`. No source gave compile-time savings in seconds.

| Proposed type | Kind | Holds or does | Must not |
|---|---|---|---|
| `EntityId` | serializable struct | Stable GUID string set once per NPC, player slot and world item | Use GameObject names or instance IDs |
| `DamageInfo` | readonly struct, passed by `in` | Attacker ID, weapon ID, amount, hit point, direction, body part, attack kind, time | Hold GameObject references |
| `DamageResult` | struct | Applied amount, blocked, staggered, downed, killed | |
| `Health` | plain C# | Current and max, `Damaged` and `Died` events, dies exactly once | Read input, clock or camera |
| `FighterStateMachine` | plain C#, `Tick(dt)` | Idle, WindUp, Active, Recovery, Blocking, Staggered, Downed, Dead | Take timing from the Animator |
| `AttackIntent` | struct | Actor ID, attack kind, aim origin, aim direction, time | Come from anywhere but an input adapter or a brain |
| `CombatRules` | pure static functions | Resolve an attack from attacker, target, weapon and query result | Use `Time.time`, `Random`, `Camera.main` or singletons |
| `MeleeWeaponDefinition` | ScriptableObject | Tuning data | Store values that change in play |
| `Fighter` | MonoBehaviour | Owns Health, state machine and weapon instance; `Submit(intent)`; runs the hit query | Know whether it is the local player |
| `MeleeHitQuery` | plain C# over physics | Swept NonAlloc queries and the per-swing hit set | Read viewmodel transforms |
| `HurtboxPart` | MonoBehaviour on bones | Body part, multiplier, owning fighter | |
| `AttackCoordinator` | plain C#, one per target | Grants attack permission | |
| `InmateBrain` | plain C#, `Tick(dt, perception)` | Returns intents; seeded random; transition log | Reference "the player" |
| Presenters | MonoBehaviours | Hitstop, camera kick, sounds, flashes, ragdoll, health display | Change rules state |

Unity's Unity 6 e-books recommend composition, ScriptableObject data, and event channels in place of singletons ([Unity design patterns e-book](https://unity.com/resources/design-patterns-solid-ebook); [Unity ScriptableObject architecture e-book](https://unity.com/resources/create-modular-game-architecture-scriptableobjects-unity-6)). An event channel is a ScriptableObject asset that broadcasters raise. Listeners subscribe in `OnEnable` and unsubscribe in `OnDisable`, and Unity names harder debugging as the cost ([Unity](https://unity.com/how-to/scriptableobjects-event-channels-game-code)). **Proposed:** use per-fighter C# events (`Damaged`, `Died`, `AttackStarted`) for anything about one fighter. The health display then subscribes to its own player's `Health`, not to a global "player health" channel that would be wrong the day there are two players. Reserve ScriptableObject channels for world-level events such as "fight started in this cell," which guards and gangs consume.

`SampleSaveData` already separates `Personal` and `World` state and carries a `version` field. **Proposed:** add player health (and any injuries) to `Personal`, add each NPC's alive, downed or dead state and health to `World` keyed by `EntityId`, bump the version, and give older saves default values. Whether bodies persist, and whether saving is allowed mid-fight, are **Open**. The simplest rule is to block saving while any fighter is in combat.

The netcode sources set the release 2 constraints. Netcode for GameObjects (NGO), Unity's networking package for GameObject projects, assumes by default "a client-server topology, in which the server owns all NetworkObjects" ([Unity](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.10/manual/terms-concepts/ownership.html)); a host is a server that also plays. Unity's guidance says "your server must have logic to validate player actions coming from clients." Its Boss Room sample "plays an animation on Melee action client side while waiting for the server to confirm the swing," and NGO has "no server side rewind implementation right now" ([Unity](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.7/manual/learn/dealing-with-latency.html)). Server-authoritative shooters rewind positions to what the attacker saw, and Valve's Source engine keeps one second of history for this ([Valve](https://developer.valvesoftware.com/wiki/Lag_Compensation)). Ubisoft's melee game For Honor instead runs a deterministic peer-to-peer simulation with rollback ([GDC Vault](https://www.gdcvault.com/play/1026322/Back-to-the-Future-Working)), and Blizzard's Overwatch kept gameplay data separate from logic ([GDC Vault](https://www.gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and)).

What to do now follows from those constraints, and each step also makes single-player testing easier. Intents from a named actor go to one entry point, which the release 2 host will later call with player 2's intents. Rules take time and state as parameters, with no hidden clock or random generator. Hit queries are built from the acting fighter's own view data, and players, NPCs and items get stable entity IDs. Presentation starts the swing animation and sound at once while the rules decide damage separately, which is the split Boss Room uses over the network. Per-player health, stamina, combat state and held weapon stay apart from shared NPC health, bodies and dropped weapons. Attack timing lives in code rather than Animator events, and hitstop applies per fighter. Equally important is what not to build now. That means no "the player" singleton, no UI or camera code that changes combat state, no combat logic in view scripts' `Update`, and no GameObject references as saved identity. A victim must never decide for itself that it was hit. There should be no NGO packages or `NetworkBehaviour` base classes, and no position-history buffer. Nor should the project move to Netcode for Entities, whose built-in lag compensation requires rebuilding the game on Unity's entity system ([Unity](https://docs.unity3d.com/Packages/com.unity.netcode@1.4/manual/physics.html)). For two cooperating players, a host-side plausibility check on distance, angle and timing is likely enough in release 2, because cheating matters less than in competitive play. That is an inference to test in release 2, not a reason to build anything now.

## Edit-mode tests and a greybox room come before the real cell

### Three fast test layers catch most combat bugs

The Unity Test Framework runs NUnit tests in both Edit mode and Play mode ([Unity](https://docs.unity3d.com/6000.2/Documentation/Manual/test-framework/test-framework-introduction.html)). Edit-mode tests run in the Editor update loop, without coroutines. Play-mode tests run as coroutines and can step frames ([Unity](https://docs.unity3d.com/6000.4/Documentation/Manual/test-framework/edit-mode-vs-play-mode-tests.html)). Both kinds run from the command line as `Unity.exe -runTests -batchmode -projectPath <path> -testResults <file.xml> -testPlatform EditMode`, filtered with `-testCategory` or `-testFilter` ([Unity](https://docs.unity3d.com/6000.4/Documentation/Manual/test-framework/run-tests-from-command-line.html)). They can also be started from code, which suits agent-driven Editor sessions ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/test-framework/running-tests-from-code.html)).

For physics, `Physics.simulationMode = SimulationMode.Script` makes physics advance only when `Physics.Simulate` is called ([Unity](https://docs.unity3d.com/ScriptReference/SimulationMode.Script.html)). Steps above 0.03 s are "likely to produce inaccurate results," and the call does not run `FixedUpdate` ([Unity](https://docs.unity3d.com/ScriptReference/Physics.Simulate.html)). Unity calls a fixed step "crucial for more reproducible physics behavior (though true determinism with PhysX has other challenges)" ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/physics-optimization-cpu-manual-simulation.html)). `Time.captureDeltaTime` advances `Time.time` by a fixed amount per frame, regardless of real time ([Unity](https://docs.unity3d.com/ScriptReference/Time-captureDeltaTime.html)).

The Input System's `InputTestFixture` gives each test a blank, isolated input system with `Press` and `Release` helpers ([Unity, 1.14 docs](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/Testing.html)). `InputEventTrace` records and replays real input, and must be disposed or it leaks native memory ([Unity](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.2/api/UnityEngine.InputSystem.LowLevel.InputEventTrace.html)). The Performance Testing package's `Measure.Frames()` records frame times after a warmup ([Unity](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.3/manual/measure-frames.html)).

Test Framework 1.6 is already installed. The project's current checks are standalone check scripts, so combat would add the first NUnit test assemblies.

| Layer (proposed) | When it runs | Covers | Example assertions |
|---|---|---|---|
| Edit mode, most tests | Every change; seconds | `Health`, `CombatRules`, `FighterStateMachine` via `Tick(dt)`, `InmateBrain` with a fixed seed, `AttackCoordinator`, weapon asset validation, save round-trip | Dies once; no damage after death; inmate wind-up of 0.6 s or more before first damage; heavy charge scales damage; old save loads with full health; every weapon has reach above zero |
| Play mode integration | Before builds | Code-built fixture with capsules, or a tiny test scene; `SimulationMode.Script` stepped with `Physics.Simulate(0.02f)`; mode restored in teardown | One swing hits a target once; rod reaches where fist misses; inmate damages an idle player within N ticks; ragdoll enabled on death |
| Input to intent | Before builds | `InputTestFixture` pressing mouse buttons | One click gives one light-attack intent for the right fighter; hold gives heavy; the talk key never produces an attack |
| Recorded scenarios | On demand | `InputEventTrace` replays against the sandbox dummy | Outcome ranges, not exact frames |
| Performance | Before gang work | `Measure.Frames()` with N brawling NPCs | Frame-time baseline kept with results |

Tag combat tests `[Category("Combat")]` so agents can run just those. Assert outcomes with margins, because physics and navigation are not bit-exact between runs.

### Build order: feel first, content last

Arkane's regret list sets the order: "The level Design was done before the combat Sandbox. -> too small environments." Blind playtesting was "the most convincing tool… I wish we had started it earlier" ([GDC 2007 talk text](https://archive.org/stream/GDC2007Colantonio/GDC2007-Colantonio_djvu.txt)). **Proposed** order for ENCOUNTER-01, with a recommended reasoning mode per step:

|---|---|---|---|

| 2 | Player fists: input adapter, intents, buffered attack, swept query, hit set; debug gizmos for reach and sweeps, plus on-screen phase text | One swing hits once; out-of-reach swings miss; button-to-swing under 100 ms | High |

| 5 | Book and rod as weapon assets; pickup reference; held item becomes equipped; the chosen armed rule | Tests show rod reach and damage differ from fists; the armed rule matches the user's decision | Medium |
| 6 | Downed state and kill action (if chosen), death presentation, saved alive/dead state, save version bump | Save and reload keep the inmate dead; an older save still loads | High: persistent state |
| 7 | Move into the NeighborCell scene; wire completion through the Rue, Dex and Harris chain; Windows build check | The full chain plays to completion in a build | High |
| 8 | Real arms rig, clips and sounds once the greybox feels right; user playtest and one uncoached tester | User approval recorded as review, never assumed | Medium |

Gizmos (Editor-only debug drawings) and on-screen phase text make the fight debuggable for agents that cannot watch it. The transition log does the same for the inmate. The coordinator's real budget, hearing and factions wait until a second hostile fighter exists.

### Assets, audio and Steam shape the schedule as much as code

Animation sourcing starts with the rig. Reusing store or Mixamo clips on the inmate requires the custom rig to import as Humanoid, which needs at least 15 bones and a T-pose. Generic clips transfer only between identical skeletons ([Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/GenericAnimations.html); [Unity](https://docs.unity3d.com/6000.3/Documentation/Manual/ConfiguringtheAvatar.html)). The first task is checking the Animation Type in the rig's import settings. Stylized, short-limbed proportions will likely need contact fixes, and the Animation Rigging IK package is not installed; no source tested this, so it is an inference.

Each clip source has a constraint. Mixamo is still free and royalty-free for games ([Adobe FAQ, search excerpt](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html)), but users reported outages in June and September 2025, and a support worker reportedly called it "not supported anymore" ([Adobe Community](https://community.adobe.com/questions-696/mixamo-service-down-589868)), so download and log any clip you plan to use now. The Unity Asset Store EULA, effective December 4, 2024, allows use in games but prohibits using assets as "inputs for artificial intelligence" without consent ([Unity](https://unity.com/legal/as-terms)). Whether an AI coding agent reading raw purchased asset files counts is untested and worth confirming before agents open such files. Cascadeur's free plan cannot export FBX and is non-commercial; Indie costs $11 a month billed annually for revenue under $100k, and retargeting is Pro-only ([Cascadeur](https://cascadeur.com/plans)). The first-person arms need their own small rig, with clips authored from the eye position.

For audio, Kenney's Impact Sounds (130 files) are CC0 ([Kenney](https://kenney.nl/assets/impact-sounds)). The Sonniss GDC bundle is royalty-free with no attribution required, but forbids AI/ML training and reselling ([Sonniss, search excerpt](https://sonniss.com/gdc-bundle-license/)). It belongs in the asset register under its own license, not as CC0. Each hit is built from layers, then trimmed: movement whoosh, contact transient, low thud, cloth or skin, and vocal effort ([Pixflow](https://pixflow.net/blog/punch-impact-sound-effects-for-fight-scenes/)). Unity's Audio Random Container varies clip, pitch and volume without code ([Unity](https://docs.unity3d.com/6000.0/Documentation/Manual/Create-randomized-playlist.html)). Recording the grunts yourself avoids licensing questions for voices.

Steam adds four constraints. Its content survey is required before review and asks for honest disclosure of violence, including content "uploaded in your builds, even if it's not accessible" ([Steamworks](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)), so a debug-only kill counts. Since November 15, 2024, Steam hides games without a valid age rating in Germany; a digital-only game can get Valve's own rating through the survey, but must not reuse an IARC-generated USK rating from another store ([Steamworks](https://partner.steamgames.com/doc/gettingstarted/contentsurvey/germany)). Australia requires classification for games sold online ([Australian Classification](https://www.classification.gov.au/for-industry/apply-for-classification/classify-computer-game)), and how a Steam-only indie game meets that is unresolved in the sources, so confirm before release. The Steam Direct fee is $100, recouped after $1,000 in adjusted gross revenue ([Steamworks](https://partner.steamgames.com/doc/gettingstarted/appfee)), and the onboarding page states a 21-day wait after paying and a Coming Soon page for at least two weeks ([Steamworks](https://partner.steamgames.com/doc/gettingstarted/onboarding)). How graphic the kill looks therefore affects store filtering and regional availability, not only tone.

## Conclusion

The research shows that, for this project, co-op readiness and agent testability are the same requirement. The choices that would let a release 2 host re-run player 2's swing are the ones that let an edit-mode test decide a fight in milliseconds with no scene: intents from a named fighter, time passed into the rules, stable IDs, queries from the attacker's own view, and per-fighter hitstop. That discipline costs almost nothing extra in release 1, and an assembly boundary makes the compiler enforce it rather than code review. The real uncertainty lies elsewhere. The research found no sourced timings for first-person melee specifically, no precedent for a cute-looking game with a deliberate kill, and no settled rating path for Australia. The user's judgment and playtesting resolve these, not more reading.

What tests cannot settle is feel and fairness, and those decide whether "real combat" works here. The references fail in the same four ways: slow input, unreadable wind-ups, misjudged distance, and levels built before combat. Each is cheaper to fix in a greybox room than in the finished cell. The armed-player question matters for the same reason: if a weapon ends the fight, the tuning work above has little left to tune. The next step is for the user to settle at least decisions 1, 4 and 5. ENCOUNTER-01 should then be planned at **High** reasoning, because it introduces combat, death and persistent character state together.
